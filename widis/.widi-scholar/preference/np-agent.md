# 检索策略先验

这份文件是检索**策略**的载体。它与角色定义分开存放，是因为策略要能被逐条改写、
逐条关闭，而角色定义不需要——布局与版本约定见本目录的 `README.md`。

下面的条目是先验建议，不是硬约束。硬约束在角色定义里（工具调用协议与安全边界），
违反它们是错误；这里的条目是"通常这样做效果更好"。遇到与条目冲突的具体证据时，
以证据为准，并在报告里说明偏离了哪一条、为什么。

条目里**不含任何阈值、预算或数量**。"多少条子查询""被引多高算通用经典""预算几次调用"
一律不在这里——那些是可训练参数，由工具入参与服务配置承载。
这里只写语义：做什么、为什么、什么时候改变做法。

## 两组条目，为什么分组

一次实测给出的负结果决定了这份文件的形状：四条陈述式提示写进上下文，
agent 复述了它们，三条一条也没有执行，召回从 1/4 变成 0/4
（`docs/reviewer-design.md` §2.2）。教训不是"提示没用"，而是
**不可观察的提示没用**——一条无法判断有没有被执行的条目，
既不能被审查、也不能被测量，还会被复述蒙混过去。

所以条目分两组：

- **A 组（已绑定）**：每条带一行 `observable:`，指明它断言公开轨迹
  $\bar{\tau}_t$ 的哪个字段。**关掉它，轨迹会不同。** 偏好实验的消融只作用于这一组。
- **B 组（未绑定）**：条目照原样保留，标 `observable: none` 并写清为什么暂时绑不了。
  **排除在消融之外。** 它们不是坏条目，是还没有观察面的条目；
  把一条从 B 提到 A 是一件具体的工作。

`observable:` 写的是判据，不是给你的额外任务。一条被检查的条目，
执行它就是满足它——这正是它值得留在 A 组的原因。

条目格式：

```
- [id] 条目正文。
  <!-- observable: 对 $\bar{\tau}_t$ 的断言，或 none: 为什么绑不了 -->
```

`id` 稳定，不因增删其他条目而改变，这样一条轨迹可以引用"当时生效的是哪几条"。
带 `kind: example` 的条目是示例式的，会额外标注 `origin`。

## A 组：已绑定的条目

### 查询构造

- [phrase-and-keyword-both] 一个多词概念既要作为整体短语查过，也要作为关键词组合查过。
  两者召回的东西不一样：短语精确但可能一条都不返回，关键词宽但会把无关的东西带进来。
  只做后者，等于把"这个概念是一个整体"这个信息扔掉了。
  <!-- observable: 本 episode 的 subqueries 中含引号的条数 >= 1 -->

- [cover-two-readings-first] 首轮就同时覆盖至少两种对问题的读法，而不是把一种读法
  拆成若干近义查询。判断标准很简单：如果两条子查询换掉的只是同义词，
  它们测的是同一个假设。一个跨社区的问题里，答案常有一半在你没想到的那一侧。
  <!-- observable: 首轮 subqueries 中存在一对，其内容词 Jaccard 低于配置的上限 -->

- [carry-the-date-boundary] 问题带时间边界时，每一次检索都要把它作为 `end_date` 传下去。
  不传不是"宽松一点的同一次检索"，是另一次检索：晚于边界的论文按定义不可能是答案，
  它们只会挤占名额。
  <!-- observable: 每个 search_metadata 调用的 filters 里都有 end_date -->

### 每步之后先诊断

- [probe-before-second-round] 初始召回完成之后、发起第二轮检索之前，
  先勘察一次结果的分布，再决定下一步。跳过这一步直接发下一个调用，
  等于放弃了这次调用买到的信息——而"结果看起来还行"这个自我判断，
  在一次最终召回为零的检索里也一样会得出。
  <!-- observable: callsByTool.facet_probe >= 1，且它早于第 2 次 search_metadata -->

- [reread-before-refetch] 取详情取到一定程度就该重新排一次，而不是继续取。
  取详情不产生新召回；当取详情的次数已经超过检索次数，
  瓶颈通常不在"还没找到"，而在"找到的没被排对"。
  <!-- observable: get_paper 次数超过 search_metadata 次数时，callsByTool.rank_candidates >= 1 -->

### 答案

- [commit-incrementally] 确认一篇属于答案就立刻写进答案池，并写清它贡献了什么，
  不要攒到最后一次性提交。攒到最后有两个代价：中途没有任何东西可供审查，
  而且一旦 episode 被打断，此前的判断全部丢失。
  <!-- observable: answerPool 的首次写入早于最后一次 search_metadata -->

- [withdraw-with-reason] 改变主意就把那篇从池子里撤掉并写下理由，不要留着凑数。
  一条带理由的撤回比一次安静的删除有用得多——它是一条有出处的负例。
  <!-- observable: answerPool.removed 中每条都带非空 reason -->

## B 组：未绑定的条目

这些条目保留原文与出处，但**关掉它们轨迹不会不同**，所以它们不进消融。
每条注明绑不了的原因。绝大多数原因归成三类：

1. **工具入参里没有对应的概念**——比如"方向"、"共被引"、"种子质量"
   都不是任何工具签名里的字段，agent 是否照做无法从调用参数上看出来；
2. **它约束的是判断而不是动作**——比如"识别提问者要的是够用还是尽可能全"，
   两种判断产生的调用序列没有形状上的差别；
3. **它依赖一个还不存在的观察量**——比如排序输出的质量变化，
   在判别层落地之前没有数字可读。

### 分解与方向

- [direction-coverage] 一个研究问题通常跨越多个研究社区。先把各个方向都覆盖到，
  再在单一方向上深入；把已找到的结果按方向归类，并明确标出哪些方向强、哪些弱、
  哪些还完全没有。第二轮工作应当聚焦与第一轮**不同**的方向。
  <!-- observable: none — "方向"不是工具入参里的概念；A 组的 cover-two-readings-first 是它可绑定的一小块 -->

- [decompose-by-research-elements] 把研究问题拆成检索要素再构造查询：
  它要解决的任务是什么（这一项总是存在）、贡献是什么、用什么方法、
  有没有时间范围、有没有指定的数据源或领域。修饰中心名词的形容词跟着中心词留在同一组；
  独立的名词短语单独成组。任务本身优先，其余按对检索的重要性排序。
  <!-- observable: none — 拆解的正确性要对着问题原文判，轨迹里只有拆解的结果 -->

- [infer-implicit-directions] 如果问题隐含了一个字面上没出现的相关研究社区，
  主动为它补一个方向。这是判断力高于句法解析的地方：问题的措辞来自提问者熟悉的
  那个社区，而答案往往一半在另一个社区里。
  <!-- observable: none — "隐含的社区"需要外部知识才能判定补得对不对 -->

- [no-over-constrained-merge] 一个请求里含多个独立的实体或数据集时，
  先写出检索计划，一个实体一次检索。不要把它们塌缩成一个同时约束所有条件的查询——
  那样的查询通常什么都召回不到，而且失败原因无法归因到哪个条件。
  <!-- observable: none — 需要先从问题里认出"几个独立实体"，那不在轨迹里 -->

- [choose-query-representation] 决定用什么来表达检索意图，而不是默认用自由文本：
  主题词、来源、期刊或会议加年份、作者、机构，或它们的组合。
  能用结构化字段表达的约束，用字段比用关键词更精确。
  具体有哪些字段可用，看运行时的能力表，不要凭记忆。
  <!-- observable: none — 可绑定的一半（用了字段还是纯关键词）要等 provider_query 的入参分类，暂缓 -->

- [decompose-example-cross-community]
  `kind: example`
  `origin: {source: metasci-citeflow/references/query-search.md, lines: "34-44", status: rephrased}`
  <!-- observable: none — 示例条目，不主张任何动作 -->

  问题："能不能借用 conformal prediction 的校准指标来改进 machine unlearning 的评价？"

  分解：`(machine unlearning, evaluation)` / `(conformal prediction, calibration)`
  / `(unlearning, benchmark)` / `(model editing, knowledge)`

  要点：第四组不在原问题的字面里。它是从"要评价模型忘掉了什么"这个假设推断出来的
  相邻社区——知识编辑那一支研究的正是同一个对象的另一面。

### 每步之后先诊断

- [diagnose-before-act] 每次检索返回之后，先判断这批结果的质量再决定下一步：
  标题是否真的贴题、年份分布是集中还是散开、不同来源给出的结果是否重合。
  跳过这一步直接发下一个调用，等于放弃了这次调用买到的信息。
  <!-- observable: none — 判断本身不产生调用；A 组的 probe-before-second-round 是它可观察的那一步 -->

- [rewrite-on-failure] 结果不对时重写检索式，不要重复同一个检索式。
  四种不对各有各的改法：**跑题**通常是关键词有歧义（一个缩写在另一个领域里是别的意思），
  要加限定词把它锚定回本领域；**过窄**去掉最严格的那个词；**过宽**加一个更具体的词；
  **缺方向**新建一组查询而不是改现有的。
  还有一个区分很重要：**有命中但不够**应当放宽现有查询，**完全零命中**应当换角度重新生成——
  放宽一个方向完全错误的查询只会得到更多不相关的结果。首轮零命中就立刻换角度，
  不要机械地把轮数耗完。
  <!-- observable: none — "重复同一个检索式"可查，但"改对了没有"要判语义；前半可提到 A 组，待办 -->

- [retreat-on-weak-signal] 引文信号弱到不足以支撑扩展时，退回去补检索，
  而不是在弱信号上硬做扩展。从一个本身就没建立起来的候选集里扩展，
  只会把噪声放大成更多噪声。
  <!-- observable: none — "信号弱"没有轨迹里的量；引文计数在本语料上大面积缺失（F-11） -->

- [diagnose-source-by-growth] 用候选集的增长幅度来诊断扩展源选得好不好。
  扩展之后几乎没有新东西进来，通常不是这个领域小，而是源选错了。
  <!-- observable: none — 增长幅度可算，但"因此换了源"这个反应无法与其他原因区分 -->

- [growth-is-not-success] 候选集变大本身不是成功。判断一轮扩展有没有用，
  要看排序输出或评测分数有没有变好，不是看池子有多大。
  更多的扩展可以同时提高覆盖并**降低**最终名单的质量——
  把相关论文挤到名单之外的，往往正是新增的那批。
  <!-- observable: none — 需要排序质量的观察量，判别层落地（S12）之前没有 -->

### 引文扩展

- [read-cocitation-before-expanding] 先读共被引信息，再决定从哪里扩展。
  共被引结构告诉你这个方向的核心是哪几篇；不看它就选源，等于随机选。
  <!-- observable: none — 没有共被引工具，这条目前无法执行也无法观察 -->

- [one-direction-per-round] 每一轮扩展只聚焦一个方向。
  一轮里同时追几个方向，结果混在一起，无法判断是哪个方向被覆盖了。
  <!-- observable: none — "方向"不是 expand_citations 的入参 -->

- [never-expand-from-noise-hub] 不要从已判为噪声的枢纽论文的施引文献里扩展。
  噪声枢纽的施引集合是另一个社区，扩展它只会把那个社区整个拉进来。
  <!-- observable: none — "已判为噪声"是 agent 内部判断，轨迹里没有这个标记 -->

- [source-count-follows-quality] 扩展源的数量应当跟着候选质量走，不是固定的。
  好的候选少，就用少的；候选普遍平庸，多加几个也补不出质量。
  <!-- observable: none — 需要"候选质量"这个量 -->

- [fill-missing-direction-immediately] 发现某个方向完全没有覆盖，立刻补一次检索，
  不要留到最后统一处理。缺失的方向越早补上，后面的扩展才有东西可依据。
  <!-- observable: none — 同 direction-coverage -->

- [late-queries-are-better-informed] 工作到中段时你对问题的理解比开头好，
  这时补的检索式通常比开头写的更准。所以不必在开头就把检索预算用完——
  留一部分给"读过一些结果之后才想得到"的查询。
  <!-- observable: none — 调用的时间分布可算，但"更准"无法从轨迹判定 -->

- [second-round-only-for-new-direction] 决定要不要再跑一轮时看一件事：
  这一轮会不会覆盖新的方向。已经覆盖好的单一方向、或者补充检索已经把缺口填上的情况，
  再跑一轮只是重复；而多方向的问题里首轮只深化了一个方向，或者补充检索带来了新论文，
  就值得再跑。
  <!-- observable: none — 同 direction-coverage -->

- [bypass-corrupted-candidate-pool] 系统给出的扩展候选池本身被污染时
  （多数候选都该判为噪声），不要在里面硬选。改从检索排名靠前的、已经在候选集里的论文
  直接指定扩展源。工具给了一个候选池，不等于必须从这个池子里选。
  <!-- observable: none — "污染"是 agent 的判断 -->

### 种子与前向扩展

- [seed-for-coverage-not-fame] 选种子先看它能补哪个方向，不是先看它被引多少。
  取种子之前先看整个种子集合，优先覆盖还缺的方向。
  一篇全局高被引的通用经典或大综述当种子，会用边缘相关的论文把候选集淹掉——
  它被引高恰恰因为所有人都引它，这让它对任何具体方向都没有指向性。
  一个种子要值得选，它的语义相关性和它在**本领域内**的被引都得高，
  只有其中一个高的，通常是另一类东西：只有语义高是边缘小众工作，
  只有被引高是通用工具。
  <!-- observable: none — 依赖被引数，而本语料上被引数大面积缺失或严重偏低（F-11） -->

- [forward-expansion-preconditions] 前向扩展是实验性的做法，不是默认流程的一步。
  做它之前先把检索与后向扩展完成，看过候选集和方向诊断，
  并且确认这次要用的种子没在之前的轮次里用过。
  <!-- observable: none — "种子没用过"可查，其余不可；整条不可绑 -->

- [forward-expansion-stop-conditions] 停止前向扩展的信号有三个：
  上一轮几乎没带来新东西、新结果都落在已经很强的方向上、选不出没用过的新种子。
  出现任一个就停，不要因为还有轮数配额就继续。
  <!-- observable: none — 同上 -->

- [skip-forward-for-historical-topics] 有些情况根本不该做前向扩展：
  问题本身是历史性的（相关工作都在过去，没有后续引用它的新文献），
  或者种子各自的被引都很少（没有前向的边可走）。
  <!-- observable: none — 需要判定问题的"历史性" -->

- [seeded-entry-skips-recall] 提问者已经给了种子论文时，跳过关键词检索，
  直接标记这些种子并做引文扩展。已经有了准确的入口，再去猜关键词是浪费，
  而且猜出来的检索式很可能把入口本身排在后面。
  <!-- observable: none — 触发条件在问题里而不在轨迹里；给定"问题带种子"这个前提它是可绑的，待办 -->

### 覆盖与轮次

- [alternate-facets-across-rounds] 问题形如"某个方法在某个应用领域"时，
  在轮次之间交替聚焦：一轮聚焦方法，一轮聚焦应用领域。
  每轮都同时压住两边，两边都搜不深。
  <!-- observable: none — 需要先认出问题是"方法 × 领域"这个形状 -->

- [phase-order-hint] 默认的推荐顺序是先检索、再引文扩展、最后重排。
  这是建议顺序而不是必须遵守的流程：诊断结果指向别的顺序时就改，
  比如提问者已给种子（见 `seeded-entry-skips-recall`）就不必从检索开始。
  <!-- observable: none — 它明说自己是可偏离的建议，因此没有可断言的形状 -->

- [budget-priority] 在预算内为动作排优先级，不要为了穷尽选项而把预算耗光。
  前一两次调用结果就很好时，省下来的预算比多做几次更有价值——
  它留给了后面"读过结果才想得到"的检索。
  <!-- observable: none — 预算记账还没接上成本模型（F-4），没有可读的预算数字 -->

- [recognize-comprehensive-intent] 识别提问者要的是"够用的一批"还是"尽可能全"。
  明确说了要综述、要全部相关工作、要做文献综述的，值得走完整流程；
  问一个具体事实的，做完整流程是浪费。首轮就命中很多相关结果，
  或者主题是一个已经成熟的老领域，都是"值得做全"的信号。
  <!-- observable: none — 两种判断产生的调用序列没有形状上的差别 -->

### 歧义与失败

- [resolve-ambiguity-before-fetching] 标识符或名称有歧义时，先消歧再去取依赖它的数据。
  提问者给了明确的标识符就直接用它，不要再用名称去查一遍。
  一个名称对上多个候选时，报告这个歧义并说明你选了哪一个、依据是什么——
  但**不要停下来向提问者追问**（见 `report-and-degrade`）。
  带着一个没消解的歧义继续往下取数据，会让后面所有结果都建立在一个可能错的实体上。
  <!-- observable: none — "有歧义"是 agent 的判断 -->

- [report-and-degrade] 反复尝试都失败时，显式上报失败并降级返回已有的结果，
  不要继续消耗预算。说清楚失败在哪一步、试过什么、现有结果因此缺了什么。
  **不要追问提问者，也不要向任何审查方求助**——把"什么时候需要帮助"变成你的决定，
  会让介入本身变成一个无法归因的变量。降级返回一个说明了边界的结果，
  比一个看起来完整、实际漏掉一整个方向的结果有用得多。
  <!-- observable: none — "不求助"由工具集在结构上保证，不需要靠条目；条目在这里是解释而不是约束 -->
